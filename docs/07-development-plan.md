# Development Plan

## 1. 계획 목적

이 문서는 현재 `docs`에 정의된 MVP 범위를 실제 개발 순서로 전환한 실행 계획이다.

핵심 목표는 아래 흐름을 하나의 운영 시스템으로 빠르게 연결하는 것이다.

- 유입
- 진단 및 첫 상담
- 교육 운영
- 후속 프로젝트 관리
- 사례 자산화
- 블로그 메일링
- 성과 리뷰

## 2. 전제 조건

이 계획은 아래 조건을 기준으로 작성한다.

- MVP는 `하나의 백엔드`, `하나의 관계형 DB`, `하나의 관리자 화면`, `하나의 메일링 서비스`를 사용한다.
- 초기 운영은 자동화보다 운영자 확인 중심으로 설계한다.
- 권한 체계, 고급 CRM, 복잡한 마케팅 자동화는 MVP 범위에서 제외한다.
- 예상 개발 체력은 `1명의 풀스택 개발자 + 1명의 운영/기획 담당 협업` 기준으로 본다.
- 전체 일정은 준비 단계를 포함해 `8주~10주`를 기준으로 잡는다.

## 3. 개발 원칙

- 먼저 저장한다.
- 그 다음 보이게 한다.
- 그 다음 분류한다.
- 마지막에 자동화한다.

추가 원칙:

- 모든 고객 접점은 반드시 백엔드를 거쳐 저장한다.
- 고객 병합은 이메일 기준으로 시작하고, 애매한 경우 운영자 검토를 우선한다.
- 태그는 초기에 10개 내외로 제한한다.
- 사례 등록은 화려한 소개보다 `문제`, `적용 방식`, `성과` 구조를 우선한다.
- 교육 회차는 최소 1개 이상의 결과물을 남기는 것을 운영 규칙으로 둔다.

## 4. 권장 구현 방향

현재 기준 권장 조합은 아래와 같다.

- 백엔드: `PHP + Laravel`
- DB: `MySQL`
- 관리자 화면: `Blade + Livewire` 또는 서버 렌더링 기반 관리자
- 파일 저장소: S3 호환 스토리지 또는 로컬 스토리지
- 메일 발송: `Brevo`, `SendGrid`, `Mailchimp` 중 webhook 지원이 단순한 서비스
- 배치 작업: `Laravel Scheduler + cron`
- 최소 비동기 처리: `Laravel Queue`

이 조합에서 중요한 포인트는 아래다.

- 빠른 CRUD 개발
- 관리자 화면 생산성
- webhook 처리 단순성
- 파일 업로드 및 로그 추적 용이성
- 작은 팀이 단일 코드베이스로 유지보수하기 쉬운 구조

## 5. 공통 개발 스트림

각 Phase와 별개로 아래 항목은 계속 병행한다.

### A. 인프라 및 배포

- 개발/스테이징 환경 구성
- 환경변수 체계 정리
- 배포 방식 결정
- DB 마이그레이션 및 백업 정책 정리

### B. 품질 관리

- 핵심 API 단위 테스트
- 주요 운영 플로우 통합 테스트
- 스테이징 데모 데이터 관리
- 에러 로깅과 기본 모니터링 설정

### C. 운영 준비

- 운영자용 상태값/태그 사전 합의
- 사례 공개 가능 범위 기준 정의
- 메일링 동의 및 수신거부 처리 기준 정리
- 교육 결과물 업로드 규칙 정리

## 7. Phase 상세 계획

### Phase 0. Foundation Setup

목표는 이후 모든 모듈이 같은 데이터 기준 위에서 개발되도록 기반을 만드는 것이다.

주요 작업:

- 프로젝트 초기화 및 기본 디렉토리 구조 확정
- 관리자 인증 방식 확정
- 공통 DB 마이그레이션 작성
- 공통 엔티티 초안 구현
  - `customers`
  - `lead_activities`
  - `customer_tags`
- 파일 저장 방식 결정
- 메일 서비스 후보 1개 선정
- 공통 UI 레이아웃과 내비게이션 구성

완료 기준:

- 스테이징에 배포 가능한 앱 골격이 있다.
- 마이그레이션과 시드가 한 번에 실행된다.
- 관리자 로그인 후 기본 화면 접근이 가능하다.

### Phase 1. Lead Intake Foundation

목표는 문의 채널을 놓치지 않고 한 화면에서 확인하는 것이다.

주요 작업:

- 교육 문의, 일반 문의, AX 진단, AX 맞춤 추천 폼 수집 API 구현
- 입력값 검증 및 유입 채널 저장
- 이메일 기준 고객 중복 처리
- `lead_activities` 타임라인 저장
- 리드 상태값 기본 적용
- 관리자 인박스 화면 구현
- 고객 목록 및 고객 상세 기본 화면 구현
- 메모와 후속 액션 날짜 입력 기능 구현

완료 기준:

- 모든 폼이 한 DB로 저장된다.
- 운영자가 신규 리드를 인박스에서 누락 없이 확인할 수 있다.
- 고객 상세 화면에서 접점 이력을 시간순으로 볼 수 있다.

### Phase 2. Diagnosis And Consultation Support

목표는 첫 상담 전에 고객 맥락을 빠르게 파악하게 하는 것이다.

주요 작업:

- `diagnosis_results` 저장 구조 구현
- 점수 계산 또는 maturity level 분류 로직 구현
- `recommendation_results` 저장 구조 구현
- 규칙 기반 추천 로직 구현
- 상담용 요약 필드 또는 요약 카드 구현
- 고객 태그 관리 기능 구현
- `case_library` 등록/검색 기본 기능 구현
- 고객 상세에 진단/추천/관련 사례 영역 추가

완료 기준:

- 상담자가 고객 상세에서 진단 결과와 추천 결과를 확인할 수 있다.
- 산업, 부서, 문제, 솔루션 기준으로 사례를 검색할 수 있다.

### Phase 3. Education Operations

목표는 교육 회차와 결과물을 고객/회사 기준으로 남기는 것이다.

주요 작업:

- `education_programs` 등록 기능 구현
- `education_runs` 생성 및 일정 관리 기능 구현
- `education_participants` 연결 기능 구현
- `education_artifacts` 업로드 및 메타데이터 저장 구현
- 교육 상태값 관리
- 후속 액션 메모 기능 구현
- 고객 상세에서 참여 교육 및 결과물 확인 기능 구현

완료 기준:

- 교육 회차별 참여 현황을 볼 수 있다.
- 결과물이 고객 또는 회사와 연결되어 저장된다.
- 교육 종료 후 후속 상담 또는 제안으로 이어질 수 있다.

### Phase 4. Project Delivery Tracking

목표는 교육 이후 컨설팅/솔루션 프로젝트 흐름을 끊기지 않게 기록하는 것이다.

주요 작업:

- `delivery_projects` 생성 기능 구현
- 프로젝트 유형 및 상태값 관리
- 프로젝트 진행 메모 기능 구현
- 중간 산출물 링크 또는 파일 저장 기능 구현
- 종료 요약과 성과 입력 기능 구현
- 고객 상세와 프로젝트 화면 연결

완료 기준:

- 고객 또는 회사 기준으로 후속 프로젝트 이력을 확인할 수 있다.
- 프로젝트별 진행 상태와 종료 결과를 저장할 수 있다.

### Phase 5. Case Capture And Reuse

목표는 교육 결과물과 프로젝트 결과를 재사용 가능한 영업 자산으로 전환하는 것이다.

주요 작업:

- `case_candidates` 등록 기능 구현
- 교육 결과물 또는 프로젝트에서 사례 후보 전환 기능 구현
- 공개 가능 범위와 검토 상태 관리
- `case_library` 승인 등록 기능 구현
- 상담/제안 중 활용할 수 있는 사례 검색 화면 보강

완료 기준:

- 교육 결과물이나 프로젝트 결과를 사례 후보로 등록할 수 있다.
- 승인된 사례를 상담자가 즉시 검색해 활용할 수 있다.

### Phase 6. Blog Mailing Loop

목표는 블로그 콘텐츠를 실제 nurture 운영에 연결하는 것이다.

주요 작업:

- `blog_posts` 등록 또는 외부 블로그 발행 정보 연동 구조 구현
- `email_campaigns` 생성 기능 구현
- 태그 및 수신 동의 기준 세그먼트 선택 기능 구현
- 메일 발송 API 연동
- `email_events` webhook 수신 처리 구현
- 고객 상세에 메일 반응 타임라인 반영
- 수신거부 처리 반영

완료 기준:

- 운영자가 블로그 글을 선택해 메일을 발송할 수 있다.
- 고객별 메일 발송, 오픈, 클릭, 수신거부 이력이 저장된다.

### Phase 7. Performance Dashboard And Hardening

목표는 어떤 흐름이 리드와 상담 전환을 만드는지 기본 수준에서 보이게 하는 것이다.

주요 작업:

- 채널별 신규 리드 수 집계
- 상태별 고객 수 집계
- 진단 완료 수 및 추천 카테고리 집계
- 교육 회차 수, 참여 현황, 결과물 수 집계
- 프로젝트 생성/완료 수 집계
- 사례 후보/승인 사례 수 집계
- 메일 발송 수, 오픈율, 클릭률 집계
- 주간 운영 대시보드 화면 구현
- 핵심 플로우 회귀 테스트와 운영 버그 수정

완료 기준:

- 운영자가 주간 기준 핵심 지표를 한 화면에서 볼 수 있다.
- 수집, 조회, 메일링, webhook, 파일 저장의 기본 안정성이 검증된다.

## 8. 우선순위가 높은 세부 결정 사항

개발 초기에 아래 6가지는 빠르게 확정해야 한다.

1. 백엔드 프레임워크 선택
2. 관리자 화면 구현 방식 선택
3. 메일 서비스 제공자 선택
4. 파일 저장소 선택
5. 퍼블릭 폼이 기존 사이트에 붙는지, 별도 페이지로 생기는지 결정
6. 운영 상태값과 태그 목록 확정

이 결정이 늦어지면 이후 API 구조와 관리자 화면 설계가 계속 흔들린다.

## 9. 테스트 및 검증 계획

각 Phase 종료 시 아래 검증을 반복한다.

- 운영 시나리오 기준 E2E 점검
- 데이터 누락 여부 확인
- 중복 고객 처리 확인
- 고객 상세 타임라인 연결 확인
- 파일 업로드/다운로드 확인
- 메일 이벤트 webhook 반영 확인

우선 검증 시나리오:

1. 교육 문의 제출 후 리드 생성, 메모 입력, 상태 변경이 되는가
2. AX 진단 제출 후 진단 결과, 추천 결과, 태그가 저장되는가
3. 교육 회차 생성 후 참여자와 결과물이 연결되는가
4. 프로젝트 종료 후 사례 후보 전환이 되는가
5. 블로그 메일 발송 후 오픈/클릭 이벤트가 고객 이력에 누적되는가

## 10. 주요 리스크와 대응

### 리스크 1. 고객 중복 병합 오류

- 대응: 초기에는 이메일 기준 자동 병합만 허용하고, 애매한 병합은 운영자 확인으로 처리한다.

### 리스크 2. 태그와 상태값 남용

- 대응: 태그는 10개 내외, 상태값은 문서 정의 범위로 제한하고 운영 가이드를 함께 만든다.

### 리스크 3. 사례 공개 범위 불명확

- 대응: 사례 후보 단계에서 공개 가능 여부, 익명화 여부, 승인 상태를 분리한다.

### 리스크 4. 교육 결과물 누락

- 대응: 교육 종료 체크리스트에 결과물 최소 1건 등록을 포함한다.

### 리스크 5. 메일링 데이터 신뢰도 부족

- 대응: 발송/오픈/클릭/수신거부 이벤트를 분리 저장하고 webhook 재처리 로그를 남긴다.

## 11. MVP 출시 기준

아래가 모두 가능하면 MVP 출시 가능 상태로 본다.

- 모든 문의 채널이 한 DB로 들어온다.
- 고객별 문의, 진단, 추천, 교육, 프로젝트, 메일 반응 이력이 한 화면에 모인다.
- 교육 회차와 결과물이 고객 또는 회사 기준으로 연결된다.
- 프로젝트 종료 결과를 사례 후보로 전환할 수 있다.
- 승인된 사례를 상담 시 검색해 활용할 수 있다.
- 블로그 글을 선택해 동의 고객에게 메일을 보낼 수 있다.
- 기본 성과 지표를 관리자 화면에서 볼 수 있다.
